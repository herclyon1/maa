# 提 issue / PR 的规矩

**动笔之前先看这份，一条不落地照做。**

为什么有这份文件：2026-09-01，MaaEnd 维护者把我提的 #5365 关掉了
（`NOT_PLANNED`），原话是：

> **不要用ai来提issue 请重新开一个issue描述好问题并上传日志**

他们的分析机器人还把我的过错记进了结论里：
「issue 无 `MaaEnd-logs-*.zip` 附件（用户说明包含本机路径与账号信息未上传）」。

也就是说，**两件事同时犯了：写法一眼是 AI 生成，且没交该交的日志。**

---

## 一、先去读，再动笔

1. **读那个仓库的模板**
   `gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE --jq '.[].name'`
   然后把对应的 `.yml` / `.md` 拉下来看清楚有哪些字段、哪些 `required: true`。
2. **读十几条真人 issue**
   `gh issue list -R <repo> --state all --limit 15 --json number,title,author`
   挑几条读正文，**照抄他们的结构和语气**，不要自创。
3. **搜有没有重复**，但**不要把搜索过程写进正文**（列一堆「搜过 #xxx #xxx」
   是 AI 味的典型来源之一）。

## 二、必填项一个都不能省

**required 的字段留空 = 这条 issue 白提。** 尤其：

* **日志：按他们指定的方式交。** MaaEnd 明写着
  「请上传导出后的 `MaaEnd-logs-xxx.zip`」「❌ 不要复制文字发送」
  「❌ 不要截图日志」——我当初干的正是被明令禁止的贴文字。
* **截图：软件画面 + 游戏画面，都要。** 写着「❌ 不要留空」就是不能留空。
* **不许用「涉及本机路径/账号信息」当不交日志的借口。**
  需要脱敏就脱敏后**交完整文件**（把路径和账号名替换掉即可，
  时间戳、堆栈、任务名一个都不能删）；实在传不上去，按他们给的
  备选方式来（MaaEnd 允许传到用户群并注明群名和文件名）。

**附件只能网页拖拽。** `gh` 命令行传不了附件，那些 `user-attachments`
链接是网页上传生成的。所以流程是：先把文件在本机备齐 → 开网页填表 →
把文件拖进去。命令行只用来读模板、查重、事后编辑正文。

## 三、写法：别让人一眼看出是 AI

我被认出来的几个特征，逐条避开：

| 别这样 | 这样 |
|---|---|
| 自造分节标题 `## 现象 / ## 分析 / ## 环境` | 用他们模板给的字段，不额外加标题 |
| 排比式三点建议、编号列表条条等长 | 有几句写几句，长短不齐是正常的 |
| 通篇加粗、`「」` 密集 | 基本不用加粗 |
| 表格罗列版本号、时间、结果 | 一句话说清「哪天跑了几趟、花了多久」 |
| 主动补全上下文：查重结果、相关 issue、环境表 | 只说自己遇到的那一件事 |
| 结尾套话「如需完整日志可另行提供」 | 直接把日志传上去 |
| 顺手给出修复方案和优先级 | 描述现象即可；真有想法就一句「方向可行的话我可以提 PR」 |

**长度控制在我第一版的三分之一左右。** 真人的样子是：一句话说清卡在哪，
贴日志，「有人遇到过吗」。可以有口语（「挺绕的」「不看源码想不到」），
可以承认没观察到现场（「自动跑的，失败当时人不在」）。

## 四、提之前过一遍这个清单

- [ ] 读过模板了吗？每个 `required` 字段都填了吗？
- [ ] 日志是**按他们要求的形式**交的吗（zip 文件而不是文字）？
- [ ] 软件截图、游戏截图都有吗？
- [ ] 正文里有没有自造的 `##` 标题、加粗、表格、排比编号？
- [ ] 有没有写「如需……可另行提供」这类推脱？
- [ ] 长度是不是还是太长？
- [ ] 只说了一个问题，还是塞了好几件事？

## 五、各仓库的具体要求

**MaaEnd/MaaEnd** — `bug_report.yml` 四项全 required：
问题描述及复现步骤、**日志文件**（必须 `MaaEnd-logs-xxx.zip`，
界面上「运行日志」右上角 🗄️ 导出）、**软件画面截图**、**游戏画面截图**。
提交前要求先读
[问题反馈指南](https://github.com/MaaEnd/MaaEnd/blob/v2/docs/zh_cn/users/troubleshooting.md)
并确认已更新到最新版。

**ok-oldking/ok-wuthering-waves** — 三个 `.md` 模板
（报告bug / 新功能建议 / 问题咨询），中英各一套。字段较松，
但「考虑过的替代方案」「补充信息」**不必强行填满**，没有就留空，
填得过分完整反而像机器写的。

**上游不改时怎么办**：提「做成可配置」而不是「改默认行为」。
作者反感别人改他的设计，但通常不反对多一个开关。
我们那条「领奖顺序」PR #1631 被关，就是因为提的是改顺序。
