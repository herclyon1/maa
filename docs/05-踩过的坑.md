# 踩过的坑

每一条都是真实发生过的，附上真正的原因。

## MaaEnd 首启窗口竞态：第一次秒败、第二次正常（2026-08-20）

一轮里 MaaEnd 第一次尝试 14 项全灭，日志只有 5 行：「窗口连接成功 →
已连接控制器[前台] → 正在连接窗口...」然后无下文。原因：游戏首次启动时
窗口会重建，MaaEnd 在窗口出现 1 秒内连接，句柄随即失效。第二次重试从
已启动的游戏接手，正常。**这类失败重试机制就是解，别按真故障处理**；
可调空间在 MaaEnd 侧的启动等待时长。同场次另一种：「打开奖励」后 20 秒
识别超时（协议空间最后一步），也是一次性的，重试自愈。
顺带：桌面别留终末地官方启动器窗口——前台控制器要求游戏窗口无遮挡。

## history 的文件名是 UTC+4，不是本机时间

AUTO-MAS 用游戏的日切时区给历史目录和文件命名：

```python
self.curdate = datetime.now(tz=UTC4).strftime("%Y-%m-%d")   # AutoProxy.py
UTC4 = timezone(timedelta(hours=4))                          # constants.py
```

这台机器跑在 UTC+8，所以**每个文件名都比真实时间早 4 小时**。

平时看不出来：只要日志里有时间戳，中继就以日志为准。
只有当一次运行**没产生带时间戳的日志**（比如游戏登录失败，还没开始就结束了），
才会退回用文件名——于是日报写出「05:17 登录失败」，而那个点机器根本没开机。

**2026-08-17 就是这么被发现的**，是操作者问「05:17 怎么可能在跑」才查出来的。


## 不要用轮询

**这是一条硬规矩，不是偏好。** 轮询是"想不出怎么被通知"时的默认动作，
在这套系统里每一次用它都被证明是偷懒。

已经改掉的：

| 原来 | 现在 |
|---|---|
| 中继每 30 秒扫一遍 history 目录 | `FindFirstChangeNotification` 挂目录变更通知，记录一落盘立即处理 |
| 每 120 秒查一次 AUTO-MAS 后端还在不在 | `OpenProcess` 拿进程句柄，进程一退出立即被唤醒 |
| Fleet Monitor 每 30 秒问一次 tailscale status | `watch-ipn-bus` 长连接，状态变了对方推过来 |
| Mac 每 10 分钟探一次游戏机在不在线好推代码 | 删掉了，改成中继开机自己去 GitHub 取 |

| 主循环每 300 秒醒来问"到点没" | 闹钟：引擎枚举出下一个确切时刻（漏跑判定 = 队列时间+25分、日报截止、检查点+2分），睡到那一刻才醒 |
| 服务器 watchdog 每 60 秒查心跳过期没 | 同上，睡到下一个判定时刻 |

时间触发的事——"过了 21:30 该发日报"、"队列到点没产出"、"检查点到了"——
确实没有文件或进程会发信号，但它们也**不需要轮询**：每一件都有确切的下一个时刻。
把这些时刻算出来、睡到最近的那个，这叫闹钟。每隔 N 秒醒来问钟表，那还是轮询。
区别不只是省电：检查点窗口只有 5 分钟，和 300 秒的醒来间隔一样宽，
相位不巧就整个错过——闹钟从结构上消灭了这类 bug。
唯一保留的定时唤醒是一小时一次的兜底，防的是"闹钟自己有 bug 导致永远沉睡"，
它兜的是底，不承担任何发现职责。

**内存采样每 10 分钟一次，那不是轮询**——它的目的就是取时间序列样本，
"事件"这个概念在那里不存在。

判断标准很简单：**你在等一件会发生的事，还是在定期记录一个状态？**
前者必须事件驱动，后者才可以定时。


## 配置的归属：AUTO-MAS 是权威，改别处等于没改

**直接改 MaaEnd 的配置无效，会被 AUTO-MAS 覆写。**
`app/task/MaaEnd/AutoProxy.py` 在启动 MaaEnd 前，会把 `ProtocolSpaceTab`、
`OperatorProgression` / `WeaponProgression` / `CrisisDrills`、以及由
`RewardsSetOption` 推导出的奖励项，全部重写进 MaaEnd 的 `optionValues`：

```python
task["optionValues"]["ProtocolSpaceTab"] = {"caseName": sanity_task_type}
for option in ("OperatorProgression", "WeaponProgression", "CrisisDrills"):
    task["optionValues"][option] = {"caseName": sanity_task_config[option]}
```

前提是该用户配置的 `Info.IfQuickConfig` 为真——这台机器上是真。

**代价是真实发生过的**：2026-08-16 12:34 有人在 MaaEnd 界面里把理智改成武器养成，
当晚 22:42 中继又往同一个文件写了一次；两次都写在会被冲掉的副本上。
真正决定刷什么的是 AUTO-MAS 的 `ScriptConfig.json`：

```
Task.SanityTaskType     哪一栏   OperatorProgression / WeaponProgression / CrisisDrills / Essence
Task.<那一栏>           哪条线   如 OperatorProgression -> OperatorEXP
Task.RewardsSetOption   A 还是 B  同一条线，A 和 B 掉的东西不同
```

**MAA 同理**：AUTO-MAS 生成 MAA 的任务表和关卡配置，直接改 MAA 的 `gui.json` 也会被覆盖。
它甚至会显式关掉 MAA 自己的每周计划（`task_set["Fight"]["UseWeeklySchedule"] = False`）。

**结论：任何自动化都必须写 AUTO-MAS 的配置，不要写下游程序的配置。**
`relay/ark_relay/sanity_plan.py` 就是按这条规则写的。

## 剿灭每次都要跑一遍，因为没有人记住"这周做过了"

现象：每次 MAA 队列产生两条记录，第一条只有 1 分钟。
那 1 分钟是剿灭作战：MAA 自己能识别本周已达上限，所以很快就退出。

`AutoProxy.py` 里：

```python
self.run_book = {"Annihilation": ... == "Close", "Routine": False}
```

`run_book` **只在内存里，每次运行重建**，所以"这周剿灭做完了"这件事没有任何地方记着。
AUTO-MAS 只提供一个静态开关 `Info.Annihilation`，取值
`Close` / `Annihilation` / `Chernobog@Annihilation` / `LungmenOutskirts@Annihilation`，
没有"每周一次"这种语义。


## 环境与连接

**`Add-WindowsCapability` 装不上 OpenSSH**
报「组件存储已损坏」。改用 [Win32-OpenSSH](https://github.com/PowerShell/Win32-OpenSSH) 的独立 MSI，一次成功。

**公钥登录一直被拒**
管理员组账户的公钥不读用户目录，必须放 `C:\ProgramData\ssh\administrators_authorized_keys`。
另外：**无需为了 SSH 去修改别人账户的密码**，公钥登录不依赖密码。

**杀毒软件把 sshd 删了**
火绒把 `sshd-session.exe` 判成 `Worm/DTStealer.B` 隔离。现象很迷惑：TCP 端口连得上、但没有 banner、立刻断开；`Restart-Service sshd` 之后服务卡在 StartPending。
**这种情况下我无法自救**——修 SSH 需要 SSH。必须人到现场。

**SSH 是单点故障**
所有远程能力都建立在它之上。已加自动重启策略，但仍需要一条非 SSH 的兜底通道（未实现）。

## 编码

**中文经过 heredoc → ssh → PowerShell 全变乱码**
stdin 被按 GBK 解码。PowerShell here-string（`@'...'@`）经过这条管道会**静默失败**——不报错，就是没执行。

可靠做法：
- 脚本在本地写好，`scp` 上去用 `-File` 执行
- **`.ps1` 文件里不要写中文**：PowerShell 默认按 GBK 读无 BOM 的 `.ps1`，中文会让引号配对错乱，报「字符串缺少终止符」
- 用 `findstr`（cmd）代替 `Select-String`
- 要返回中文：远端 `[Convert]::ToBase64String(...)`，本地解码

**路径末尾的反斜杠会吃掉引号**
`"D:\path\to\dir\"` 里的 `\"` 被当成转义。去掉末尾反斜杠，或用变量拼接。

## GUI 自动化

**SSH 会话截不了图**
Windows session 0 隔离，SSH 会话没有桌面，`CopyFromScreen` 直接失败。
解法：动作脚本挂成计划任务在交互式会话里跑，SSH 只负责 `schtasks /run` 触发。

**点击总是落在错误的窗口上**
连续两张截图对比发现窗口有 30 像素的层叠偏移 → 说明中间有新窗口出现过。
真凶：`schtasks /run` 拉起了一个**可见的 PowerShell 控制台**，抢走焦点并盖住屏幕左半边。**自动化把自己要点的目标挡住了。**
解法：计划任务加 `-WindowStyle Hidden`。
副作用：控制台被点中后进入「选择」标记模式会冻结输出，需要发一次 `{ESC}`。

**正则改 JSON 漏改并误伤**
要关掉 3 个 webhook 任务，只成功 2 个：第 3 个的 JSON 里 `taskName` 和 `enabled` 之间夹了个 `customName`，正则没匹配上，反而误伤了 `recentlyClosed` 里的历史记录。
**是结构化 diff 抓出来的**——把改动前后的 JSON 都拍平成 `路径 → 值` 再对比。从此每次改配置都必做这一步。

## 配置陷阱

**模拟器类型写错会静默启动错误的实例**
写成 `general` + `dnplayer.exe` 时，`Index=1000` 被完全忽略，启动的是另一个模拟器实例，没有任何报错。
必须是 `ldplayer` + `ldconsole.exe`——源码里 `EMULATOR_PATH_BOOK["ldplayer"]["executables"][0]` 就是它，校验器会拒绝其它值。

**MAA v5.1 有两个配置文件**
`gui.json` 是废弃的旧格式，`gui.new.json` 才是真正在用的。只读前者会得到完全过时的信息（比如以为外部通知没配置）。

**AUTO-MAS 的通知有三层开关**
`SendTaskResultTime`（全局）→ `IfSendStatistic`（全局/用户级）→ `IfServerChan` + key（全局/用户级）。
只开其中一两个等于没开。曾经把用户级 `IfServerChan` 打开却没开 `IfSendStatistic`，一条都发不出去。

**AUTO-MAS 的开机自启不是注册表项**
是个叫 `AUTO-MAS_AutoStart` 的计划任务（登录触发）。查注册表 Run 和启动文件夹都找不到，会误判成"没配自启"或"配了但没生效"。
而且 `set_SelfStart()` 实测**没能成功创建它**，需要手动建。

**`StartUpEnabled` 分不清早上和晚上**
它的语义是「程序一启动就跑」，而开机这个动作早晚一模一样。BIOS 唤醒会让它在晚上多跑一整轮。详见 [配置清单](02-配置清单.md)。

**MaaEnd 的 webhook 任务发不出内容，这是结构性的**
`__MXU_WEBHOOK__` 就是 GET 一个写死的 URL，`title` / `desp` 硬编码在地址里。它拿不到运行结果，换谁配都一样。

## 推送

**企业微信 `errcode=60020`**
调用方 IP 不在「企业可信IP」里。曾经因为填的时候少打了 IP 开头的一位数字，排查了很久——**这个错肉眼极难发现，务必逐位核对**。

**企业微信 `errcode=44004 empty content`**
测试用的中文内容被 GBK 管道搞没了。用纯 ASCII 测试内容验证链路通不通。

**Server酱返回 `code:0` 但手机收不到**
消息通道配的是 PushDeer 而不是方糖服务号。返回码只说明 API 调用成功，不代表消息送达。

**`sctp...` 和 `SCT...` 是两套东西**
`sctp` 开头是 Server酱³（App 优先），`SCT` 开头是 Turbo（支持方糖服务号，即一层微信服务号通知）。

## 推送

**一个渠道坏掉，会让告警刷屏一整夜，还让机器不关机**

原来的 `Notifier.send()` 只要**任一**渠道抛异常就返回非空错误列表，而引擎把「非空」当成「整条没发出去」：

```python
errors = self.notifier.send(title, body)
if errors:
    return              # 保留在磁盘上，下一轮重发
```

于是当企业微信坏了、Server酱正常时：消息其实**已经送达**，但引擎不销账 —— 同一条告警每 30 秒重发一次；日报的 `mark_report_sent` 永远不被调用，也整夜重发；而 `_maybe_shutdown` 要求 `_pending` 清空且日报已发，所以**机器再也不会关机**。

这不是假想。两台机器都在**家宽拨号后面，公网 IP 会变**，而企业微信自建应用只接受可信 IP 列表内的调用（`errcode=60020`）。IP 变的那天，上面三件事同时发生。

**修法：至少一个渠道送达 = 已送达。** `send()` 只在**所有**渠道都失败时才返回错误。同时坏掉的渠道作为一条**独立故障**报出来（走还活着的渠道），每进程每渠道只报一次 —— 机器一天开关两次，所以没修好就会不断重新提醒。60020 会附上可操作提示，直接告诉你去后台重加 IP。

**一次 TLS 握手超时就丢一条告警**

从日本发往 `sctapi.ftqq.com` 偶尔会在握手阶段超时，下一次重试却 1 秒就回。告警是一次性的，没有任何东西会替它重发 —— 丢了就是丢了。

已加传输层重试（3 次，退避 1.5s 递增）。**但只对传输故障重试**：HTTP 状态码是"服务器回答了"，403 重试一万次还是 403，`errcode=60020` 同理，这些立刻抛出，好让调用方赶紧换端点或换渠道，而不是白白干等退避。

顺带查明：Server酱³ 那个按 uid 推导出来的 `{uid}.push.ft07.com` 端点对我们这个 key **恒返回 403**，它从来就不是有效兜底。真正能用的只有 `sctapi.ftqq.com`。

**日报的触发条件写错了，队列一提前就永远发不出，机器还永远不关机**

原来的判断是「**最后一次运行的结束时刻** ≥ ARK_LAST_RUN_AFTER」：

```python
last_finished = max(结束时刻 for e in entries)
cutoff = last_finished.replace(hour=21, minute=30)
if last_finished < cutoff:
    return          # 永远成立
```

队列在 21:30、21:52 跑完 → 正常。但队列一旦提前到 **21:25 且 21:28 跑完**，结束时刻永远小于 21:30，这个 return **永远命中**，日报一辈子发不出去。而 `_maybe_shutdown` 又要求日报已发 —— **机器永远不关机**。

而且 `_maybe_daily_report` 和 `_maybe_shutdown` 各算各的 cutoff，两份重复实现，起点还不一样。

**修法：cutoff 统一由 `_report_cutoff()` 提供，取自 AUTO-MAS 自己配置里最后一个队列时刻**（读不到才回退到 `ARK_LAST_RUN_AFTER`），判断改成「时钟过了 cutoff 且没有脚本在跑」。这样在 AUTO-MAS 里改队列时间，日报和关机自动跟上，不用记得同步改环境变量。

**GBK 控制台放不下 ✅**

`print("\n✅ 配置可用")` 在 GBK 代码页下直接 `UnicodeEncodeError`，`check` 和 `test` 都是**在最后那行成功提示上崩掉** —— 活干完了，命令却报失败退出。日志的 StreamHandler 同样编不出来，`logging` 自己吞异常所以循环不挂，但带 emoji 的日志行会从 stderr 静默消失（写文件那路是 UTF-8，不受影响）。

修法：`main()` 一开始就 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。附带好处是输出文件从此是 UTF-8，SSH 取回来直接可读，不用再 base64。

**根治要靠固定 IP。** 把云服务器（静态 IP）加进白名单一次，两台机器都通过它推送，就再也不受拨号 IP 变动影响 —— 这同时也是补上「机器没开机」「中继自己挂了」两个盲区的唯一办法。

## 判断失误

**把时区差当成系统时钟故障**
服务器 Asia/Shanghai，用户 Asia/Tokyo，差 1 小时。曾把这个差值当成 NTP 不同步，差点去跑 `w32tm` 修一个不存在的问题。
**所有人类可读的时间戳都必须标注时区。**

**先动手写轮子，后搜有没有现成的**
一开始写了约 1000 行的 Python runner，后来发现 AUTO-MAS 已经把这些全做了（调度队列、日志监控、失败重启、多脚本多账号），而且做得更好。那 1000 行全删了。
**先搜再写。**

## AUTO-MAS 的通知有两套开关，用户级那个管不住「任务结果」推送

2026-08-20 连查两轮才定位。现象：把两个用户的「启用通知」都关掉之后，
手机上仍然收到 `[MAA] 任务已全部完成！(用时 0h 1m 0s)`。

源头在 AUTO-MAS 自己（MAA 目录下全文搜不到任何 Server酱 key，MAA 发不了），
判定代码在 `app/task/MAA/tools/notify.py`：

```python
if mode == "任务结果" and (
    Config.get("Notify", "SendTaskResultTime") == "任何时刻"
    or (Config.get("Notify", "SendTaskResultTime") == "仅失败时"
        and message["uncompleted_count"] != 0)
):
```

所以：

| 开关 | 位置 | 管什么 |
|---|---|---|
| `Notify/Enabled`（每个用户一份） | `config/ScriptConfig.json` | 该用户的通知总闸 |
| **`Notify/SendTaskResultTime`（全局）** | **`config/Config.json`** | **「任务结果」推送，取值 `不推送` / `任何时刻` / `仅失败时`** |

**用户级关掉不影响全局那条路径**——这就是关了还在响的原因。
2026-08-20 已把全局设为 `不推送`（Server酱 key 保留原样，不要靠删 key 来消音：
删 key 会连带影响其它用途，且掩盖真正的开关）。

## AUTO-MAS 运行中会用内存值覆写 config

同日两次实锤：收件箱在晚班运行期间写下的 `WaitTime=120` 被冲回 `60`；
剿灭闸门写下的 `Annihilation=Close` 被冲回打开（于是每轮又空跑一次剿灭，
每次约 1 分钟外加一次完整的游戏启动）。

规矩：**改 AUTO-MAS 的 config 必须避开脚本运行期**。
`Engine.scripts_running()` 就是为这件事准备的；收件箱路径当时没调用它，已补上，
推迟的指令会在脚本停下后自动补做。剿灭闸门也改成幂等的 `enforce()`，
被冲回后能重新关上（原来 `done_week` 一匹配就直接返回，一漏就漏一整周）。

## MAA 的掉落统计是累计值，不能相加

2026-08-21 体检发现。一轮里刷了两批，MAA 打了两个掉落块：

```
TO-5 掉落统计:
龙门币 : 1440 (+1440)      ← 第一批后的累计
当前次数 : 10
...
TO-5 掉落统计:
龙门币 : 2448 (+1008)      ← 第二批后的累计，不是本批增量
当前次数 : 7
```

我们的解析器把两个块的 `龙门币` 相加，得出 **3888**，真实值是 **2448**（最后一块即答案，
括号里的 `(+N)` 才是增量）。AUTO-MAS 自己取的就是最后一块，两边一对就露馅了。

**规矩：掉落取最后一块的值，不要累加。** 但 `当前次数` 相反——`10` 和 `7` 是分批数，
相加得 17 才对（日志里写着「开始行动 1~10 次」「开始行动 11~17 次」）。同一个块里
两种语义并存，容易一起搞错。

## 把 AUTO-MAS 的用户名改成 ASCII

历史目录是用账号名命名的（原来叫「新用户」「默认用户名」）。中文目录在 Windows 上完全
合法，但经 SSH 取回来是 GBK，是所有监控脚本输出乱码的根源。2026-08-21 已改名为
`arknights` / `endfield` 并迁移全部历史目录。

**改名必须连带改写中继的 `seen.txt`**：记录的唯一标识是 `<日期>/<用户名>/<时间>`，
只改目录不改清单，中继会把全部历史记录当成新纪录重新告警一遍。

## 终末地的「启动后等待」最小值是 60 秒，写小了会被静默改回

2026-08-21 实测：把 `Game/WaitTime` 改成 30，写盘成功、回读也是 30，但 **AUTO-MAS
下次启动时把它改回了 60**，没有任何提示。

原因在 AUTO-MAS 自己的配置模式（`app/models/schema.py`）：

```python
WaitTime: Optional[int] = Field(default=None, ge=60, description="游戏等待时间")
```

`ge=60` 就是硬下限。中继的 `set_wait_time` 已经把范围收紧到 60–600 并给出明确
提示，免得再出现"改了、看着生效了、其实被改回去了"这种最难查的情况。

**同类风险**：AUTO-MAS 的其它数值字段也可能有 `ge`/`le` 约束。以后改配置发现
"改完又变回去"，先去 schema.py 看有没有约束，别急着怀疑写盘失败。
