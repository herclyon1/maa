# 中继设计

> 状态：**设计阶段，尚未实现**
> 最后更新：2026-08-15

## 1. 中继要解决什么

现状的三个痛点：

| 痛点 | 现状 |
|---|---|
| 通知太吵 | 一轮 5+ 条空消息，有用信息为零 |
| 失败发现太晚 | 靠人肉翻手机通知，经常错过 |
| **机器没开机时毫无察觉** | 收到的"安静"和"一切正常"长得一模一样 |

前两条已经通过配置改善（见 `02-配置清单.md`）。**第三条是中继存在的根本理由。**

## 2. 核心矛盾：监督者不能住在被监督者体内

如果中继跑在那台 Windows 上：

```
机器没开机 → 中继也没跑 → 没人发现机器没开机
```

这是个死结。**中继必须在一台"永远醒着"的机器上。**

## 3. 宿主选型

### ❌ 方案 A：跑在 Windows 服务器本机

- 优点：零成本、零延迟、直接读文件
- 致命缺陷：**机器每天只开机约 3 小时**（09:00–10:25、21:20–22:15），其余 21 小时中继不存在
- 结论：可以做"失败告警 + 日报"，**做不了开机监督**

### ❌ 方案 B：跑在 Mac 上

**合盖必睡。** macOS 在系统层面强制：合上盖子且没有外接显示器时进入睡眠。

绕过办法都不可行：
- `caffeinate` —— 对合盖无效
- `sudo pmset -b disablesleep 1` —— 有效，但需要管理员密码、机器持续发热耗电
- Clamshell 模式 —— 需要常插电源 + 外接显示器，等于 Mac 不能离开桌子

而这台 Mac 的实际使用方式是**每天带出门**。宿主必须固定不动。

- 结论：**不适合**

### ✅ 方案 C：便宜云服务器（推荐）

- 7×24 在线，不睡、不出门、不跟着人走
- 成本约 ¥60–90/年（轻量应用服务器最低配即可，中继是个几十 MB 的 Python 进程）
- **放境内**：Windows 那台在中国，境内互通稳定；推 Server酱/企业微信也快

## 4. 三层架构

```
┌─ 第一层：执行层（Windows，中国，每天开机约 3 小时）──────┐
│  AUTO-MAS ─┬─ MAA      （明日方舟）                      │
│            └─ MaaEnd   （终末地）                         │
│  产出 → history/<日期>/<用户>/<时分秒>.json               │
└──────────────────────────────────────────────────────────┘
                    │
                    │  ① 事件：新的 history JSON 出现就 POST
                    │  ② 心跳：开机期间每 5 分钟 POST 一次
                    │     （走 Tailscale 内网，不暴露公网）
                    ▼
┌─ 第二层：中继层（云服务器，7×24）────────────────────────┐
│  接收 + 落库（SQLite）                                    │
│  ├─ 事件是失败 → 立刻推                                   │
│  ├─ 事件是成功 → 静默记账                                 │
│  ├─ 当天最后一轮结束 → 生成日报 → 推                       │
│  └─ 到点没收到心跳 → 推「机器没起来」告警  ★ 关键         │
│  Claude Sonnet 5 负责措辞，不负责判定                     │
└──────────────────────────────────────────────────────────┘
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   企业微信（你）           Server酱（bro）
```

## 5. 心跳：区分"安静"和"正常"的唯一办法

中继内置日程表（服务器/北京时间）：

| 时刻 | 期望 |
|---|---|
| 08:45 | 米家通电，机器应开机 → 5 分钟内应收到心跳 |
| 09:00 | 新队列应启动 |
| ~10:25 | 新队列应完成 → 收到 2 条事件（MAA + MaaEnd）→ 机器关机，心跳停止 |
| 21:20 | BIOS 唤醒 → 应收到心跳 |
| 21:30 | Evening-MAA 应启动 |
| ~22:15 | 应完成 → 1 条事件 → 关机 |

任一环节超时 → 告警，并说清楚**卡在哪一环**：

- 08:50 还没心跳 → 「机器没开机」（米家没执行？BIOS 设置丢了？断电没恢复？）
- 有心跳但 09:10 还没开始 → 「AUTO-MAS 没启动或定时没触发」
- 开始了但超时未完成 → 「任务卡死」

**这是本地中继永远做不到的事。**

## 6. 关机权必须交给中继

**这是一条会推翻现有配置的连锁反应，务必记住。**

现在两个队列都是「完成后操作 = 关机」，AUTO-MAS 跑完立刻断电，采集层来不及把最后一条事件送出去。

中继上线后要改成：

```
AUTO-MAS 完成后操作 = 不操作
        ↓
采集层确认事件已送达云端（收到 ACK）
        ↓
采集层自己执行 shutdown /s
```

**顺序**：先用现有配置（AUTO-MAS 自己关机）把无人值守流程跑通验证 → 中继上线后再移交关机权。**在中继写好之前不要动。**

## 7. Claude API 的定位

**用 Sonnet 5。** 只负责措辞，不负责判定：

```
代码负责（确定性）          模型负责（措辞）
─────────────────          ──────────────
是否失败                    把日志片段翻译成人话
哪个任务失败                把当天数据组织成可读日报
关卡 / 掉落 / 理智数字
起止时间
心跳超时判断
```

理由：判定错了是事故，措辞差了只是难看。把判定留给代码，模型抽风的后果被限制在"话说得不好听"。

生成日报时把原始 history JSON 一并附上，数字对不上时能一眼回溯源头。

**用量**：日报每天 1 次（输入约 2000 token、输出约 400），失败诊断一周一两次。一年不到 100 万 token。

## 8. 数据通道：复用 Tailscale

Windows 和 Mac 已经在同一个 tailnet 里：

```
Mac      100.110.87.36   macbook-air
Windows  100.65.39.119   ins
云服务器  (加入后自动分配)
```

云服务器装上 Tailscale 加入同一账号即可。好处：

- 不用给云服务器开公网端口
- 不用做鉴权（tailnet 内已是可信网络）
- 中国 ↔ 云服务器走 Tailscale 直连或 DERP 中继，都通

## 9. 分阶段落地

**阶段一（不花钱，现在就能做）**
中继主体跑在 Windows 本机：失败立即推 + 每日汇总。
覆盖不了「机器没开机」，但前两个痛点先解决。

**阶段二（买服务器后）**
把中继整体搬到云端，Windows 上只留采集层（读文件 + POST + 心跳）。
**采集层的代码不用改**——所以阶段一写的时候就要把「采集」和「判定推送」拆成两个模块。

**阶段三（可选）**
双向对话：从微信发指令回来（今天跳过/换关卡/立刻跑一轮）。
