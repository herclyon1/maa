# 中继设计

> 状态：**设计阶段，尚未实现**
> 最后更新：2026-08-15

## 1. 中继要解决什么

现状的三个痛点：

| 痛点 | 现状 |
|---|---|
| 通知太吵 | 一轮 5+ 条空消息，有用信息为零 |
| 失败发现太晚 | 靠人肉翻手机通知，经常错过 |
| **机器没开机时毫无察觉** | 收到的"安静"和"一切正常"长得一模一样 |

前两条已经通过配置改善（见 `02-配置清单.md`）。**第三条是中继存在的根本理由。**

## 2. 核心矛盾：监督者不能住在被监督者体内

如果中继跑在那台 Windows 上：

```
机器没开机 → 中继也没跑 → 没人发现机器没开机
```

这是个死结。**中继必须在一台"永远醒着"的机器上。**

## 3. 宿主选型

### ❌ 方案 A：跑在 Windows 服务器本机

- 优点：零成本、零延迟、直接读文件
- 致命缺陷：**机器每天只开机约 3 小时**（09:00–10:25、21:20–22:15），其余 21 小时中继不存在
- 结论：可以做"失败告警 + 日报"，**做不了开机监督**

### ❌ 方案 B：跑在 Mac 上

**合盖必睡。** macOS 在系统层面强制：合上盖子且没有外接显示器时进入睡眠。

绕过办法都不可行：
- `caffeinate` —— 对合盖无效
- `sudo pmset -b disablesleep 1` —— 有效，但需要管理员密码、机器持续发热耗电
- Clamshell 模式 —— 需要常插电源 + 外接显示器，等于 Mac 不能离开桌子

而这台 Mac 的实际使用方式是**每天带出门**。宿主必须固定不动。

- 结论：**不适合**

### ✅ 方案 C：便宜云服务器（推荐）

- 7×24 在线，不睡、不出门、不跟着人走
- 成本约 ¥60–90/年（轻量应用服务器最低配即可，中继是个几十 MB 的 Python 进程）
- **放境内**：Windows 那台在中国，境内互通稳定；推 Server酱/企业微信也快

## 4. 三层架构

```
┌─ 第一层：执行层（Windows，中国，每天开机约 3 小时）──────┐
│  AUTO-MAS ─┬─ MAA      （明日方舟）                      │
│            └─ MaaEnd   （终末地）                         │
│  产出 → history/<日期>/<用户>/<时分秒>.json               │
└──────────────────────────────────────────────────────────┘
                    │
                    │  ① 事件：新的 history JSON 出现就 POST
                    │  ② 心跳：开机期间每 5 分钟 POST 一次
                    │     （走 Tailscale 内网，不暴露公网）
                    ▼
┌─ 第二层：中继层（云服务器，7×24）────────────────────────┐
│  接收 + 落库（SQLite）                                    │
│  ├─ 事件是失败 → 立刻推                                   │
│  ├─ 事件是成功 → 静默记账                                 │
│  ├─ 当天最后一轮结束 → 生成日报 → 推                       │
│  └─ 到点没收到心跳 → 推「机器没起来」告警  ★ 关键         │
│  Claude Sonnet 5 负责措辞，不负责判定                     │
└──────────────────────────────────────────────────────────┘
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   企业微信（你）           Server酱（bro）
```

## 5. 心跳：区分"安静"和"正常"的唯一办法

中继内置日程表（服务器/北京时间）：

| 时刻 | 期望 |
|---|---|
| 08:45 | 米家通电，机器应开机 → 5 分钟内应收到心跳 |
| 09:00 | 新队列应启动 |
| ~10:25 | 新队列应完成 → 收到 2 条事件（MAA + MaaEnd）→ 机器关机，心跳停止 |
| 21:20 | BIOS 唤醒 → 应收到心跳 |
| 21:30 | Evening-MAA 应启动 |
| ~22:15 | 应完成 → 1 条事件 → 关机 |

任一环节超时 → 告警，并说清楚**卡在哪一环**：

- 08:50 还没心跳 → 「机器没开机」（米家没执行？BIOS 设置丢了？断电没恢复？）
- 有心跳但 09:10 还没开始 → 「AUTO-MAS 没启动或定时没触发」
- 开始了但超时未完成 → 「任务卡死」

**这是本地中继永远做不到的事。**

## 6. 关机权必须交给中继

**这是一条会推翻现有配置的连锁反应，务必记住。**

现在两个队列都是「完成后操作 = 关机」，AUTO-MAS 跑完立刻断电，采集层来不及把最后一条事件送出去。

中继上线后要改成：

```
AUTO-MAS 完成后操作 = 不操作
        ↓
采集层确认事件已送达云端（收到 ACK）
        ↓
采集层自己执行 shutdown /s
```

**顺序**：先用现有配置（AUTO-MAS 自己关机）把无人值守流程跑通验证 → 中继上线后再移交关机权。**在中继写好之前不要动。**

## 7. Claude API 的定位

**用 Sonnet 5。** 只负责措辞，不负责判定：

```
代码负责（确定性）          模型负责（措辞）
─────────────────          ──────────────
是否失败                    把日志片段翻译成人话
哪个任务失败                把当天数据组织成可读日报
关卡 / 掉落 / 理智数字
起止时间
心跳超时判断
```

理由：判定错了是事故，措辞差了只是难看。把判定留给代码，模型抽风的后果被限制在"话说得不好听"。

生成日报时把原始 history JSON 一并附上，数字对不上时能一眼回溯源头。

**用量**：日报每天 1 次（输入约 2000 token、输出约 400），失败诊断一周一两次。一年不到 100 万 token。

## 8. 数据通道：复用 Tailscale

Windows 和 Mac 已经在同一个 tailnet 里：

```
Mac      100.x.x.x   <控制端主机名>
Windows  $ARK_HOST   <服务器主机名>
云服务器  (加入后自动分配)
```

云服务器装上 Tailscale 加入同一账号即可。好处：

- 不用给云服务器开公网端口
- 不用做鉴权（tailnet 内已是可信网络）
- 中国 ↔ 云服务器走 Tailscale 直连或 DERP 中继，都通

## 9. 分阶段落地

**阶段一（不花钱，现在就能做）**
中继主体跑在 Windows 本机：失败立即推 + 每日汇总。
覆盖不了「机器没开机」，但前两个痛点先解决。

**阶段二（买服务器后）**
把中继整体搬到云端，Windows 上只留采集层（读文件 + POST + 心跳）。
**采集层的代码不用改**——所以阶段一写的时候就要把「采集」和「判定推送」拆成两个模块。

**阶段三（可选）**
双向对话：从微信发指令回来（今天跳过/换关卡/立刻跑一轮）。

## 10. 优先复用的现成轮子

原则：**通用的部分一律不自己写**，只写别人做不了的领域逻辑。

### Uptime Kuma —— 心跳监督 + Web UI + 告警分发

[uptime.kuma.pet](https://uptime.kuma.pet/) · 开源自建

它的 **Push 监控**就是标准的"死人开关"：给你一个 URL，被监控方定期 curl 一下；**过了间隔没收到就告警**。这正是第 5 节要的心跳机制，不用自己实现。

一次性解决三件事：

| 需求 | Uptime Kuma 提供 |
|---|---|
| 机器没开机的告警 | Push 监控（心跳超时） |
| 手机上能看状态 | 自带 Web UI，浏览器直接开 |
| 告警发到微信 | 95+ 通知渠道，含企业微信 |

部署：云服务器上一条 Docker 命令。

### onepush / Apprise —— 推送渠道适配

写自己的日报推送时，不要手写各家 API：

- [onepush](https://pypi.org/project/onepush/) —— 国内渠道为主，**原生支持 Server酱、企业微信应用、企业微信机器人**，最贴合本项目
- [Apprise](https://github.com/caronc/apprise) —— 151 个服务，国际化更全，企业微信走 webhook 机器人

### 分工

```
Uptime Kuma（现成）          自己写（约 150 行）
──────────────────          ──────────────────
心跳 / 开机监督              读 AUTO-MAS 的 history JSON
手机可看的 Web UI            提取关卡 / 掉落 / 理智 / 起止时间
告警渠道分发                 判定成功失败
                            调 Sonnet 生成日报和人话诊断
                            推送（用 onepush）
```

**只有"读 AUTO-MAS 的运行记录并生成含掉落的日报"是没有轮子的**，因为那是这个项目独有的领域逻辑。

## 11. 部署形态：不做 exe，做无头服务 + Web UI

### 为什么不是 exe 桌面程序

技术上完全能做（Python + PySide6 + PyInstaller）。但要问一句：**这个 exe 双击运行在哪台机器上？**

- 跑 Windows 服务器 → 回到"监督者住在被监督者体内"
- 跑云服务器 → 云主机通常没有桌面，GUI 没有意义
- 跑 Mac → 合盖就睡

而且**主要使用场景是在日本用手机**——exe 在手机上打不开。

### 正确形态

**中继本体 = 无头常驻服务 + 内置 Web UI**

- 手机浏览器打开就能看，不用装任何东西
- 顺便承载双向控制：网页上放按钮（今天跳过 / 立刻跑一轮 / 换关卡）
- 云端和本机跑同一份代码

Uptime Kuma 本身就是这个形态，可以直接参照。

### exe 唯一合适的位置

**Windows 上的采集端**做成托盘小程序是合理的：有托盘图标、能看到本机状态、能手动触发一次上报。这个用 PyInstaller 打包成 exe 没问题。

但**中继本体不该是 exe**。

## 12. 本机模式与服务器模式都要能跑

同一份代码，两种部署模式，靠启动参数切换：

```bash
ark-relay --mode local     # 跑在 Windows 上，直接读 history 目录
ark-relay --mode server    # 跑在云服务器上，接收 HTTP 上报
```

代码结构必须一开始就拆开：

```
collector/     采集：读 history JSON、发心跳          （两种模式共用）
core/          判定、记账、日报生成、Sonnet 调用       （两种模式共用）
transport/     local = 直接函数调用
               server = HTTP 收发                     （唯一的差异层）
notify/        推送出口（onepush）                     （两种模式共用）
```

**只有 `transport/` 一层不同。** 这样阶段一在本机跑通之后，阶段二搬到云上不用重写任何业务逻辑。

本机模式的能力边界要写清楚：它能做失败告警和日报，**唯独做不了开机监督**——因为机器没开机时它自己也不存在。这不是实现缺陷，是物理限制。

## 13. 四端客户端：用 PWA，不写四套原生

需求是 Android / iOS / Windows / macOS 都能用。

| 方案 | 代码量 | iOS 上架 | 结论 |
|---|---|---|---|
| 四套原生 | 4 份 | 要 | 不现实 |
| Electron + React Native | 2 份 | 要 | 仍需上架，维护翻倍 |
| **PWA（网页）** | **1 份** | **不要** | ✅ |

PWA 在 iOS / Android 上「添加到主屏幕」后就是一个 App 图标，点开全屏、没有浏览器边框，用起来和原生 App 没有区别；Windows / Mac 直接浏览器打开。**一份代码、零应用商店、零安装包、改完刷新就更新。**

推送通知不走 PWA——已经有企业微信和 Server酱，比 PWA 推送可靠得多。网页只负责「看状态」和「发指令」。

## 14. 双向链路

```
        [你的手机 / 任意设备]  PWA 网页
                │
                │  人类语言：「今天别刷了」「换成 CE-6」「理智药只用 3 个」
                ▼
        ┌─ 中继（云服务器，7×24）──────────────────────┐
        │                                              │
        │  上行（你 → 机器）                            │
        │   1. Sonnet 解析意图 → 结构化指令              │
        │      {action:"set_stage", value:"CE-6"}       │
        │   2. 回推确认卡片：「要把关卡从 TO-5 改成       │
        │      CE-6，确认？」← 你点确认才入队            │
        │   3. 存入指令队列（机器不在线就等着）           │
        │                                              │
        │  下行（机器 → 你）                            │
        │   4. 收 history 事件 → Sonnet 翻成人话 → 推    │
        │   5. 心跳超时 → 告警                          │
        └──────────────────────────────────────────────┘
                │  ▲
      开机后拉取 │  │ 回报执行结果
                ▼  │
        ┌─ Windows 采集端 ─────────────────────────────┐
        │  白名单校验 → 备份 → 改配置 → JSON 校验        │
        │  → 结构化 diff → 不符立即回滚                  │
        └──────────────────────────────────────────────┘
```

**关键点**：指令是**存起来等机器上线**的，不要求你发指令时机器开着。你在上班路上说「今天换 CE-6」，机器晚上 21:20 醒来时自己就改好了。

## 15. 安全护栏：AI 改配置必须有约束

让模型把人话翻译成配置文件改动，**不能无人复核直接落地**。这个项目里改过 4 处配置，每一处都靠结构化 diff 验证过，并且**真的抓到过一次漏改 + 误伤**（见 [踩过的坑](05-踩过的坑.md)）。模型不会比正则更谨慎。

四道闸，缺一不可：

**① 白名单，不允许任意改 JSON**

模型只能产出预定义动作，不能输出 JSON 补丁：

```
set_stage(关卡)              改刷哪一关
set_medicine(数量)           理智药上限
toggle_task(任务名, 开/关)    开关某个任务
skip_today(队列名)           今天跳过
run_now(队列名)              立刻跑一轮
```

不在这张表里的意图 → 拒绝，并回复「这个我做不了，需要人工改」。

**② 执行前人工确认**

模型解析出意图后，先把「我理解你要把 X 从 A 改成 B」推回给你，**你点确认才入队**。这一步不能省——人话本来就有歧义，「别刷了」是今天跳过还是永久停用？

**③ 落地时复用现有的安全流程**

和手动改配置完全一样：备份 → 改 → `json.loads()` 校验 → 结构化 diff 核对「新增 0 / 删除 0 / 改动 N」。**任何一项不符立即回滚备份。**

**④ 回报**

执行成功 / 失败 / 被白名单拒绝，都推回给你。不能出现「发了指令，然后没有下文」。

## 16. 这套东西真正解决的问题

现在的控制链：

```
你 → Claude（跑在你 Mac 上）→ SSH → Windows
        ↑ Mac 关机、合盖、或你没打开 Claude —— 链就断了
```

即使 Mac 开着，也需要你主动开对话、我在场才动手。**这不是自动化，是远程人肉。**

中继上线后：

```
你（任意设备的浏览器）→ 中继（7×24）→ Windows
```

不依赖 Mac、不依赖 Claude 会话、不依赖任何一台会睡觉的机器。**这是整个项目最终要达成的形态。**
