## 一、它到底解决什么问题（先说清楚，不然做了也白做）

现在整套东西有一个结构性缺陷：**中继跑在它自己要监控的那台机器上**。

游戏机 08:40 上电、跑完、关机。如果某天它根本没开机、或者开机后中继没起来，
**没有任何人会知道** —— 因为唯一会说话的那个进程本身就没运行。你不会收到"出错了"，
你会收到"什么都没有"，而"什么都没有"和"今天很顺利"长得一模一样。

第二台机器常年在线，它能干的五件事，每一件都是现在做不到的：

| # | 能力 | 现在为什么做不到 |
|---|---|---|
| 1 | **外部观察者**：09:05 还没收到游戏机的心跳 → 立刻告诉你"他今天没开机" | 观察者和被观察者是同一个进程 |
| 2 | **指令下发不再靠 GitHub**：`queue/config.json` 直接从它这儿取 | 现在走 raw.githubusercontent，实测 10 次成功 7 次 |
| 3 | **我的落脚点**：随时有个乌鲁木齐的 shell，不用等游戏机醒着才能查东西 | 游戏机一天只醒三小时 |
| 4 | **安卓 App 的后端**：你要的"远程开关今天早/晚检查点"，那个开关得存在某个常年在线的地方 | 没有这个地方 |
| 5 | **同一局域网 → 网络唤醒**：给游戏机发 magic packet 远程开机 | 需要局域网里有台醒着的机器 |

第 5 条就是你之前问的"BIOS 能不能远程控制"的真答案：不需要 BIOS 远程管理，
只要局域网里有个邻居能发 WoL 包。前提是插座这时候是通电的（插座断电时主板没有待机电，
WoL 不成立，那种情况还是得用插座自己的 App）。

## 二、核心判断：它不需要公网地址

那台机器没有管理员权限、没有公网 IP、在 CGNAT 后面。听起来"当服务器"不成立，
但服务器需要的从来不是"一个能被连进来的地址"，而是**一条长期存在的、由它主动发起的连接**，
外面的人接到这条连接的另一端上。

方向反过来，穿透问题就消失了。

### 为什么不是 Tailscale

这条路我们这次已经验证死了：Windows 版 `tailscaled` 创建控制管道时把
`\\.\pipe\ProtectedPrefix\Administrators\Tailscale\tailscaled` 的属主
**硬编码成了 Administrators SID**。不是配置项，是源码里写死的。
`--tun=userspace-networking` 只绕开了虚拟网卡驱动，绕不开这个管道。
没有管理员就是起不来，不用再试了。

### 所以是 cloudflared

单个 exe，用户态进程，不装驱动不装服务不要管理员。它主动连出去到 Cloudflare 边缘，
外面通过一个 HTTPS 域名进来，反向送到这台机器的 localhost 端口。

它能转发的不只是 HTTP —— `tcp://` 模式可以把任意 TCP 隧道出去，包括 SSH。

## 三、部署（全程不需要管理员）

### 3.1 先做这一件事：确认 Cloudflare 边缘从乌鲁木齐通不通

**整个方案成立与否只取决于这一条。** 在那台机器上：

```powershell
curl.exe -sS -o NUL -w "%{http_code} %{time_total}s`n" https://cloudflare.com/cdn-cgi/trace
```

回 `200` 且耗时在一秒内 → 往下走。超时或连不上 → 跳到第五节的备选。

### 3.2 下载 cloudflared

```powershell
mkdir $env:USERPROFILE\srv; cd $env:USERPROFILE\srv
curl.exe -L -o cloudflared.exe https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe
.\cloudflared.exe --version
```

GitHub releases 从那边是通的（配置下发这条路一直在走同一个域）。

### 3.3 先用快速隧道验证一次

不需要 Cloudflare 账号、不需要域名，一条命令就有公网地址：

```powershell
.\cloudflared.exe tunnel --url http://localhost:8787
```

它会打印一个 `https://<随机词>.trycloudflare.com`。把那个地址发我，我从大阪连一次，
**这就证明了整条链路通**。缺点是每次重启地址都变，所以只用来验证，不用来长期跑。

### 3.4 长期方案：命名隧道

需要一个 Cloudflare 账号和一个域名（域名十几块钱一年，这是整个方案唯一的花销）。

```powershell
.\cloudflared.exe tunnel login          # 浏览器里授权，选那个域名
.\cloudflared.exe tunnel create urumqi
```

然后写 `%USERPROFILE%\.cloudflared\config.yml`：

```yaml
tunnel: urumqi
credentials-file: C:\Users\<用户名>\.cloudflared\<隧道ID>.json
ingress:
  - hostname: relay.你的域名
    service: http://localhost:8787       # 中继服务端
  - hostname: ssh.你的域名
    service: ssh://localhost:2222        # 给我的 shell
  - service: http_status:404
```

```powershell
.\cloudflared.exe tunnel route dns urumqi relay.你的域名
.\cloudflared.exe tunnel route dns urumqi ssh.你的域名
.\cloudflared.exe tunnel run urumqi
```

地址从此固定。

### 3.5 给我一个 shell（sshd 免安装跑法）

Win32-OpenSSH 的绿色包不用 `Add-WindowsCapability`，也不用注册成服务 ——
以普通用户身份、监听一个大于 1024 的端口就行：

```powershell
cd $env:USERPROFILE\srv
curl.exe -L -o ssh.zip https://github.com/PowerShell/Win32-OpenSSH/releases/latest/download/OpenSSH-Win64.zip
Expand-Archive ssh.zip -DestinationPath openssh
cd openssh
.\ssh-keygen.exe -A -f .          # 在当前目录生成主机密钥，不碰 C:\ProgramData
```

写 `sshd_config`（就放在 openssh 目录里）：

```
Port 2222
HostKey ssh_host_ed25519_key
AuthorizedKeysFile .ssh/authorized_keys
PasswordAuthentication no
PubkeyAuthentication yes
```

我的公钥放进 `%USERPROFILE%\.ssh\authorized_keys`（我另外发你），然后：

```powershell
.\sshd.exe -f sshd_config
```

注意：**不要用管理员组的账号跑这个**。管理员组账户的公钥不读用户目录、只读
`C:\ProgramData\ssh\administrators_authorized_keys`，那个路径要管理员才写得进去。
这里没有管理员权限反而正好，普通用户就读 `~/.ssh/authorized_keys`。

我这边连的时候：

```bash
cloudflared access ssh --hostname ssh.你的域名
```

### 3.6 开机自启（用户级，不要管理员）

两条都不需要管理员，选一条：

```powershell
# 启动文件夹：最简单
$s = "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\srv.cmd"
@"
start "" /min "$env:USERPROFILE\srv\cloudflared.exe" tunnel run urumqi
start "" /min "$env:USERPROFILE\srv\openssh\sshd.exe" -f "$env:USERPROFILE\srv\openssh\sshd_config"
"@ | Out-File -Encoding ascii $s
```

⚠️ **这两种都要求用户已经登录**。"不登录也运行"的计划任务需要保存密码并授予
「作为批处理作业登录」权限，那是管理员的事。所以这台机器必须是开机就进桌面的状态。
如果它有开机密码，得先关掉（`netplwiz` 里取消勾选"要使用本计算机，用户必须输入…"，
这个不需要管理员，只需要知道该账号自己的密码）。

同时要关掉休眠，否则它睡着了就不是服务器了：

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
```

（这两条普通用户对当前电源计划是能改的。改不动说明有组策略，那再说。）

## 四、跑起来之后放什么上去

按上线顺序，每一步都能单独验证：

1. **开机信标**（半天）
   不是"每分钟心跳"——那是轮询思维。游戏机开机时 POST 一条信标，
   之后每个运行记录落盘时（目录变更事件驱动）再各推一条。
   服务端在 09:05 定一个闹钟：到点没收到今天的信标 → Server酱 推"他今天没开机"。
   一条信标 + 一个闹钟，补上第 1 条，也是现在最大的窟窿。

2. **配置下发改推送**（一小时）
   游戏机对服务端保持一条长轮询请求（HTTP long-poll：服务端握着请求不放，
   有新配置才应答，55 秒无事就空应答重挂）。配置一变，秒级到达，
   而不是"下次开机才取到"。GitHub 降级为备份源。10/10 取代 7/10。
   现有的 agent 模式（`cmd_agent`，从未部署过）是按定时循环写的，
   **上线前按这个事件驱动方案重写，不带着轮询上线。**

3. **事件汇总**（一天）
   现在的日报是游戏机自己发的，关机前发不出去就丢了。改成事件实时推到服务端，
   由服务端负责发报告 —— 游戏机关不关机都不影响。

4. **安卓 App 的后端**（等做 App 的时候）
   一个 `/checkpoint` 接口，存"今天早上/晚上要不要检查"两个布尔值。
   游戏机在 09:00 / 21:30 读它。App 只是这个接口的界面。

5. **WoL**（十分钟，但要先确认插座是通电的）
   `/wake` 接口，往游戏机 MAC 发 magic packet。

## 五、如果 Cloudflare 边缘不通

那 cloudflared 就地作废，别硬试。换 **frp 或 rathole + 一台便宜 VPS**：
原理完全一样（内网机器主动连出去，VPS 转发），区别只是落脚点从 Cloudflare 换成你自己的 VPS。
香港/日本的轻量服务器一年一百多块，从乌鲁木齐连过去比 Cloudflare 稳定得多。
客户端同样是单个 exe、用户态、不要管理员。

**最坏情况**：连出去的路一条都没有。那第 1、2、4 条能力还剩多少？
第 1 条不受影响 —— 它只需要那台机器能**发出**请求（Server酱、GitHub 都验证过是通的）。
真正丢掉的是"我能连进去"这一条，也就是我的 shell。那种情况下它还是个有用的监工，
只是我要改东西得靠你复制粘贴。
